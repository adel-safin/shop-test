# Магазин цифровых товаров

Витрина по макету плюс бэкенд, который выдаёт ключ ровно один раз: под двойным кликом, под штормом
вебхуков и после сбоя поставщика. Тестовое задание.

Стек: Node.js 20, Express, PostgreSQL 16. Фронт на чистом HTML/CSS/JS без сборщика, отдаётся тем же
сервером. Зависимостей в проекте две: `express` и `pg`.

## Запуск

```bash
docker compose up -d db     # Postgres на localhost:5433
npm install
npm run db:reset            # схема + сид: 12 товаров, 50 ключей, 4 промокода
npm start
```

- витрина: http://localhost:3000
- админка: http://localhost:3000/admin.html (токен `dev-admin-token`)
- заглушки поставщиков: http://localhost:3001

Порт 5433, чтобы не спорить с локальным Postgres на 5432. Своя база подключается через
`DATABASE_URL`.

## Как обеспечена однократная выдача

Три независимых барьера. Каждый работает сам по себе, любые два можно выключить.

1. Блокировка заказа. Обработка вебхука и запуск выдачи идут внутри
   `select ... from orders where id = $1 for update`. Пятьдесят параллельных вебхуков встают в
   очередь; первый доставляет, остальные видят финальный статус и выходят.
2. Уникальность в схеме, а не в коде. `deliveries.order_id` это PRIMARY KEY, `deliveries.key_id`
   и `product_keys.order_id` под UNIQUE, `event_id` в `payment_events` тоже PK. Второй записи
   физически некуда встать, даже если логика ошибётся. Захват ключа идёт одним
   `update ... where id = (select ... for update skip locked limit 1)`, без проверки «сначала
   посмотрим, потом запишем».
3. Идемпотентность поставщика. `request_id` выводится из номера заказа (`req_<order_id>`), а не
   генерируется на каждую попытку. Повтор после таймаута приходит с тем же id и получает из журнала
   поставщика тот же код, а не следующий ключ из пула.

Ни одна из транзакций не держится поверх HTTP-вызова: выдача разбита на «занять заказ», «сходить к
поставщику», «записать результат».

## Сбои и восстановление

`created -> paid -> delivering -> delivered`, ветки `payment_failed`, `out_of_stock`,
`delivery_failed`. Переходы проходят через матрицу в `src/domain/status.js`, финальные статусы не
переписываются: `failed`, пришедший после `paid`, ничего не откатывает.

Пустой пул даёт `out_of_stock` без исключения и без 5xx. Такой заказ виден в админке в списке
«оплачен, но не выдан», рядом кнопка повторной выдачи. Повтор идёт тем же путём и идемпотентен:
если ключ уже выдан, возвращается он же.

Фоновый reconciler раз в 3 секунды подбирает заказы, зависшие в `delivering` (воркер умер посреди
доставки), восстановимые после пополнения пула и оплаты, чей вебхук пришёл раньше заказа.

Про таймаут поставщика. Явная ошибка (4xx/5xx с телом) приходит до захвата ключа, поэтому переход на
резервного поставщика безопасен. Таймаут означает «исход неизвестен», и тогда fallback запрещён:
повторяем того же поставщика с тем же `request_id`, пока он не ответит определённо. Заглушка
специально устроена так, чтобы ошибка отдавалась до `update` пула, иначе это правило было бы
неверным.

## Промокоды

Лимит расходуется одной строкой:

```sql
update promocodes set used_count = used_count + 1
 where code = $1 and used_count < max_uses returning *;
```

Ноль строк это исчерпанный лимит. Плюс `check (used_count <= max_uses)` в схеме. Инкремент при
создании заказа, возврат при `payment_failed`.

Скидку считает сервер: цена берётся из БД по `sku`, промокод из БД по коду, из тела запроса
приходят только `sku` и `code`. Поля `amount` в запросе нет вообще. Сумма из вебхука сверяется со
своей, расхождение попадает в лог, но заказ по данным клиента не переписывается. Всё в копейках
целыми числами.

## Интерактив на витрине

1. Карусель баннера: автопрокрутка 5 секунд, стрелки, точки-индикаторы. Пауза под курсором и в
   фоновой вкладке.
2. Кнопка «Каталог»: клик открывает, повторный клик, клик вне меню и Escape закрывают.
3. Переключатель валют `$ ₸ ₽`: меняет активное состояние, пересчёта по ТЗ нет.
4. Иконки сервисов: подъём с тенью при наведении.
5. Карточки товара: подъём, тень и обводка при наведении.

Отзывы, футер, мобильная и тёмная версии не верстались.

## Поведение витрины

Пул ключей заполнен только для `KEY-CS2-PRIME`, там виден основной путь: заказ, оплата, ключ на
странице статуса. Остальные товары покупаются тоже, но уходят в `out_of_stock` и появляются в
админке. Это не поломка, а второй сценарий: пополнить пул и выдать повторно.

Кнопка «Купить» не блокируется после клика намеренно, чтобы двойной клик было видно вживую. Защиту
даёт `Idempotency-Key`, стабильный на время запроса, и уникальный индекс по нему в БД.

## API

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/products` | каталог с остатком ключей |
| POST | `/api/orders` | создать заказ, заголовок `Idempotency-Key`, тело `{sku, promocode?, order_id?}` |
| GET | `/api/orders/:id` | статус и код |
| POST | `/api/promocodes/preview` | серверный расчёт скидки |
| POST | `/webhook/payment` | вебхук по контракту, всегда быстрый 200 |
| POST | `/api/dev/pay/:id?outcome=success\|fail` | заглушка платёжки, шлёт вебхук сама |
| GET | `/api/debug/orders/:id` | заказ плюс счётчики выдач, событий и свободных ключей |
| POST | `/provider/{a\|b}/issue` | поставщики на порту 3001 |

Под `X-Admin-Token`: `GET /admin/orders`, `POST /admin/orders/:id/redeliver`,
`GET|POST|DELETE /admin/keys/:sku`, `GET /admin/promocodes`, `POST /admin/reconcile`,
`POST /admin/providers/:name`.

## Настройки

Всё через переменные окружения, значения по умолчанию в `src/config.js`.

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `DATABASE_URL` | `postgres://shop:shop@localhost:5433/shop` | подключение к БД |
| `ADMIN_TOKEN` | `dev-admin-token` | заголовок `X-Admin-Token` |
| `PROVIDER_TIMEOUT_MS` | `2000` | таймаут запроса к поставщику |
| `PROVIDER_RETRIES` | `2` | повторов после таймаута, тем же `request_id` |
| `STALE_DELIVERING_MS` | `4000` | после этого `delivering` считается брошенным |
| `PROVIDER_A_ERROR_RATE` | `0` | доля явных ошибок, ключ не расходуется |
| `PROVIDER_A_TIMEOUT_RATE` | `0` | доля зависаний до захвата ключа |
| `PROVIDER_A_LOST_RATE` | `0` | доля потерянных ответов, ключ уже выдан |

Те же три доли есть у поставщика B. Их можно менять на лету:
`POST /admin/providers/a {"errorRate": 1}`.

## Структура

```
src/
  domain/      статусы и расчёт цены, без БД и HTTP
  db/          весь SQL
  services/    заказы, вебхуки, доставка, reconciler, админка
  providers/   заглушки поставщиков A и B
  api/         роуты и Express
public/        витрина, страница заказа, админка
db/            schema.sql и сид
tests/         сценарии гонок
.cursor/rules/ правила для кода: конкурентность, бэкенд, фронтенд, тексты
```
